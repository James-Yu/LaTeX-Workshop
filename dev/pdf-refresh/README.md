# PDF refresh loading-task ownership

## Problem and mechanism

The user reports repeated grey embedded PDF panes during automatic builds. This visible failure has NOT been reproduced. Worker accumulation was reproduced; its relationship to the grey pane remains a hypothesis.

Refresh calls `pdfjsLib.getDocument(...).promise`, then passes the document to `PDFViewerApplication.load()`. The application does not thereby acquire the new loading task. This bypasses normal ownership and can leave workers alive across refreshes.

The patch uses `PDFViewerApplication.open()` instead. In the bundled PDF.js application, this awaits `close()` when a loading task exists, then stores the new task. Closing destroys the previously owned task and resets application state. URL and CMap options are preserved. The viewer interface gains the matching declaration.

## Investigation and evidence

1. The installed 10.20.0 viewer was matched against a build of commit `1de2b7f854a6ccfa3375580b889339a54771b0bc`.
2. Instrumenting real browser Worker construction/termination in isolated VS Code showed 31 created, zero terminated, and 31 live after 30 baseline refreshes. No grey-screen reproduction was observed.
3. Broader experimental implementations passed earlier 1,000-cycle tests. A separate companion extension was used successfully for writing. Neither result validates this exact patch.
4. Current upstream commit `2f5a60a11a99f33013c1235f0499546cc831cfcb` still contains the ownership bypass. This focused patch was prepared against it.
5. A new run on a generated three-page PDF observed 24 created, 23 terminated, one live, and maximum one live worker. The overall run DID NOT PASS: its visible-render wait timed out. See `evidence/current-run.json`. These are teardown observations, not a passing full stress test.

The harness was subsequently adjusted to allow hidden documents to skip the visible-paint wait. That adjustment has not yet been rerun. It may address a visibility-dependent harness failure; it is not a proven diagnosis of that timeout.

The earlier baseline used a private manuscript, which is not included. The new fixture is generated from public literal text. Heap measurements are diagnostic, not proof of bounded process memory. Listener counts only instrument public on/off calls, whereas PDF.js also uses internal subscription paths; they are not asserted as reliable leak measurements.

## Reproduction

Requirements: normal repository Node/npm dependencies, Python 3, and the VS Code application executable. The developer harness has only been exercised on macOS.

```sh
npm ci
npm run compile
npm run lint
python3 dev/pdf-refresh/run.py --code "/Applications/Visual Studio Code.app/Contents/MacOS/Code" --cycles 30
```

The script prints its temporary directory. It creates an isolated profile, extension directory, synthetic PDF/source, logs, and results JSON. It opens a visible development window; place that window on the desired display. No existing project is used and no TeX installation is needed. Auto-build and extension updates are disabled only in the disposable profile.

Instrumentation is inserted into a temporary viewer.html before PDF.js starts. Each loop waits for an actual replacement document, checks rendering unless hidden, checks page preservation and one live worker, then allows the existing upstream one-second timer to finish. This tests sequential replacements, not overlapping rebuilds.

For comparison, preserve the harness, restore only the two production files from the base commit, compile, and run with `--baseline`. This records accumulation without asserting one live worker. Restore and recompile the patch afterward.
